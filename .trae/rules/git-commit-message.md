# Commit 书写规范

## 一、目标读者与判断标准

读者是三个月后的自己和一位没参与本次改动的工程师。验收标准一句话：**不读 diff，只读 commit，能回答"改了什么、为什么改、有没有风险、怎么验证的"。**

## 二、标题

- 格式 `type(scope): 摘要`，摘要不超过 50 个汉字，不加句号。
- 摘要写**行为变化**，不写文件名、函数名、模块名。"更新 PostsPage.tsx"不合格，"原始动态独立成页并支持筛选排序"合格。
- 一个提交含多个同级改动时，标题取影响面最大的一项，其余进正文分节。
- 禁止"若干优化""多项修复""细节调整"这类零信息概括。

## 三、正文六节结构

正文应该按这个结构和顺序组织内容，没有的可省略。

1. **背景**：现状哪里不对、触发这次改动的现象或需求。一到两句，说清为什么非改不可。
2. **改动**：按影响域分节（前端页面 / 后端接口 / 数据模型 / 文档），每条一个完整句子，含对象、动作、结果。禁止只列模块名或一对关键词。
3. **接口与兼容性**：HTTP 路径与参数的增删、默认值变化、数据库 schema 变化、路由变更、旧路径是否保留。无变动的省略。
4. **文档**：同步修改了哪些文档或说明文件、改了哪类内容。无变化时写"无改动"。
5. **验证**：测试代码变动和测试结果。只在重大变更或新增测试时着重书写，构建和测试通过等必走流程不要写。
6. **未完成 / 已知问题**：本次刻意没做的代码改动及原因，或引入的临时妥协。没有则省略。

破坏性变更单独起一段，以"破坏性变更："开头。

## 四、语言

- 用完整句子。允许分点，但每条必须能独立读懂，不依赖上下文。
- 禁止斜杠堆词。"导航与页脚按用户页拆层"要写成"导航栏只保留活动相关三项，源健康入口移到页脚"。
- 禁止自造压缩词（"拆层""分档""收敛一下"）。术语首次出现给全称或一句话定义。
- 数字必须带单位与口径：写"搜索防抖 300ms"、"limit 上限 200"，不写"加了防抖"。
- 参数名、字段名、路径用反引号包裹，保持与代码一致。

## 五、长度

- 单文件小改：标题 + 1~3 句正文。
- 涉及 5 个以上文件或跨前后端：正文不少于 200 字，六节齐全。
- 长度由信息量决定，不由字数指标决定；写不出内容的节直接删，不要用"等""若干"填充。

## 六、提交粒度

- 一个提交对应一个可独立回滚的主题，回滚后主分支仍可构建。
- 功能、文档重写、格式化混在一个提交时，正文必须分节说明，不能压成一条 bullet。
- 纯格式化、纯重命名、纯依赖升级单独提交。

## 七、提交前自检

- 标题描述的是行为变化，不是文件改动。
- 正文提到的每一项都能在 diff 里找到对应。
- diff 里的每个主要改动都能在正文里找到对应，重点检查文档、配置、schema、路由。
- 接口参数名、默认值、兼容性已写清。
- 已写明实际执行的验证命令与结果。
- 没有斜杠堆词、自造缩写、"等""若干"。
- 三个月后的人据此能判断要不要回滚。
